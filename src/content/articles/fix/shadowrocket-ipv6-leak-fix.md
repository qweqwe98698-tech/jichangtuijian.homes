## 双栈普及之后，泄漏面被悄悄放大了一倍

过去几年国内移动网络的演进有一个不太被普通用户感知、但对代理链路影响极大的变化：IPv6 从“试点”变成了“默认”。三大运营商的蜂窝网络基本完成 IPv6 单栈化改造，5G 终端入网时直接拿到 /64 前缀与 IPv6 默认路由；家庭宽带侧的光猫与路由器普遍开启双栈，iOS 设备在 Wi-Fi 下同时持有 A 记录与 AAAA 记录两条出网路径。

代理客户端的工作原理，本质上是在设备上抢一张路由表。iOS 上的 Shadowrocket 通过 Network Extension 框架申请 TUN 虚拟网卡，把默认路由指向 utun 接口，再由用户态进程读取 IP 包、按规则分流、封装进代理协议发往远端。问题就出在这张路由表的覆盖范围上。大量客户端的历史实现只处理 IPv4，IPv6 的默认路由依然指向 en0（Wi-Fi）或 pdp_ip0（蜂窝），于是出现一个非常隐蔽的状态：浏览器打开 IPv4 站点走代理，打开 IPv6 站点直连出网，用户看到的页面一切正常，出口地址却分裂成两个。

这种分裂在探测面板上会暴露得非常彻底。ipleak.net 会同时列出 IPv4 与 IPv6 出口，whoer.net 会把地址族、ASN、地理坐标并列展示。当 IPv6 那一栏显示的是你所在城市的运营商地址，而 IPv4 一栏显示的是节点机房地址，泄漏就已经发生，且与节点质量无关，纯粹是本地路由接管不完整。

### 为什么 IPv6 泄漏比 IPv4 泄漏更难被察觉

IPv4 时代的泄漏通常是“代理没生效”，表现为网页打不开或速度异常，用户立刻能感知。IPv6 泄漏恰恰相反，它不影响可用性。目标站点若同时有 A 与 AAAA 记录，Happy Eyeballs 算法会优先尝试 IPv6，连接成功、页面秒开，用户主观体验甚至更好，因为走的是本地直连的低延迟路径。泄漏在体验层面是隐形的，只在地址归属层面留下痕迹。

更麻烦的是 DNS 链路。iOS 的解析器在双栈环境下会并发查询 A 与 AAAA，若代理客户端的 DNS 劫持只覆盖了 IPv4 的 DNS 服务器地址，AAAA 查询可能经本地运营商解析器完成，返回的 IPv6 地址带有明显的地区属性。这条链路同时构成 DNS 泄漏与 IPv6 泄漏，两者在探测面板上往往成对出现。

## 协议栈视角下的接管断点

要修好这个问题，得先看清数据包从应用到网卡之间到底经过了哪些环节，哪一环断了。

### TUN 驱动与路由优先级

iOS 的 Network Extension 提供 Packet Tunnel Provider，客户端创建 utun 接口后通过 `NEPacketTunnelNetworkSettings` 声明要接管的网段。声明里有一个关键字段 `includedRoutes`，它决定哪些目标地址被导入隧道。若配置只写了 `0.0.0.0/0`，IPv6 的 `::/0` 就不在接管范围内，内核转发表里 IPv6 默认路由仍指向物理接口。

路由匹配遵循最长前缀优先。即便客户端声明了 `::/0`，若物理接口同时存在一条更具体的 `2408:8000::/20` 运营商路由，发往该前缀的包仍会走物理口。这就是为什么有些配置“看起来开了 IPv6”，实测仍有部分地址段泄漏。完整的接管需要 `::/0` 加上对物理接口具体路由的覆盖，或者干脆把物理接口的 IPv6 地址摘除。

```json
{
  "tunnel": {
    "ipv4": {
      "includedRoutes": ["0.0.0.0/0"],
      "excludedRoutes": []
    },
    "ipv6": {
      "includedRoutes": ["::/0"],
      "excludedRoutes": []
    },
    "dns": {
      "servers": ["198.18.0.2", "fd00:6968:656e::2"]
    }
  }
}
```

上面这段结构对应客户端内部下发给系统的网络设置。注意 DNS 服务器同时给了 IPv4 与 IPv6 两个地址，若只给 IPv4，系统的 AAAA 查询会回退到物理接口的解析器，泄漏从这里开始。

### DNS 解析链路的三段式结构

iOS 的 DNS 解析在代理场景下分为三段。应用发起 `getaddrinfo`，系统解析器读取当前网络服务的 DNS 配置；若 TUN 接管了 DNS，查询被送往客户端内置的 DNS 模块；客户端按规则决定走远端解析还是本地解析。

远端解析（Fake-IP 或远端 DNS）把域名交给节点侧解析，本地只拿到一个映射地址，运营商看不到查询内容。本地解析则由客户端代发查询到指定上游。两种模式在 IPv6 上的差异极大：Fake-IP 模式下若映射池只有 IPv4 段，AAAA 查询会返回空，应用回退到 IPv4，反而规避了泄漏；远端解析模式下 AAAA 记录被完整返回，若路由未接管，泄漏立刻发生。

### IP 属性识别机制

探测面板判定“真实地址”的依据不止一个 IP。ipleak.net 会收集 HTTP 头中的出口地址、通过 WebRTC 的 STUN 绑定请求获取候选地址、以及 DNS 解析请求的源地址。三者中任意一个暴露本地地址族，面板就会标红。

WebRTC 的机制值得单独说。浏览器通过 `RTCPeerConnection` 向 STUN 服务器发送绑定请求，STUN 响应里携带服务器观察到的源地址。若该请求走了物理接口，返回的就是本地公网地址。iOS 上 Safari 的 WebRTC 实现受系统策略约束，候选收集范围有限，但在双栈 Wi-Fi 下仍可能上报 IPv6 候选。这个通道与应用层代理无关，只与网络层路由有关，所以修复 IPv6 路由接管的同时也就堵住了 WebRTC 的 IPv6 候选泄漏。

## 在探测面板上精准复现泄漏

复现是排查的第一步，方法要能区分“代理没生效”与“仅 IPv6 绕过”。

### ipleak.net 的读法

打开 ipleak.net，页面会自动发起多组探测。重点看三个区块。第一块是顶部的 IP 地址列表，正常情况下应只显示节点出口的一个 IPv4 与一个 IPv6（若节点支持双栈）。若出现两个不同归属地的地址，且其中一个属于本地运营商 ASN，泄漏成立。

第二块是 DNS 泄漏检测，它会列出解析请求的出口。若列表里出现本地运营商 DNS 的地址，说明 AAAA 查询绕过了隧道。

第三块是 WebRTC 检测，若候选地址里出现 `2408:`、`2409:`、`240e:` 开头的国内 IPv6 段，说明浏览器的候选收集走了物理接口。

### whoer.net 的交叉验证

whoer.net 的优势在于把地址族、ASN、时区、语言并列展示，便于判断一致性。开启代理后访问，若“IP”栏显示节点地址而“IPv6”栏单独列出本地地址，或匿名度评分因地址族不一致被扣分，即可确认。它的 DNS 检测区块同样会列出解析出口，与 ipleak.net 交叉比对可以排除单一面板的误报。

### 用 curl 做命令行级验证

面板之外，命令行能给出更干净的证据。在 iOS 上可通过快捷指令调用，或在同一网络下的电脑上验证同一条链路。

```bash
## 查询 IPv4 出口
curl -4 -s https://ipinfo.io/ip

## 查询 IPv6 出口
curl -6 -s https://ipinfo.io/ip

## 查询双栈出口归属
curl -s https://ipinfo.io/json | jq '{ip, org, country, city}'
```

若 `-4` 返回节点地址而 `-6` 返回本地运营商地址，接管断点就在 IPv6 路由。若 `-6` 直接超时，说明 IPv6 已被正确阻断或未分配，属于安全状态。

## Shadowrocket 侧的三条修复路径

修复不需要三选一，按场景叠加使用最稳。核心目标是让 IPv6 流量要么进隧道，要么不出网。

### 路径一：开启客户端 IPv6 转发支持

Shadowrocket 的设置里有与 IPv6 相关的开关，作用是让客户端具备处理 IPv6 目标与 IPv6 出站的能力。开启后，客户端会在 TUN 设置中声明 `::/0` 接管，并在规则匹配时对 IPv6 目标做解析与分流。

操作顺序如下。进入设置页，找到与 IPv6 相关的选项并打开；随后进入当前配置的编辑界面，确认 TUN 相关的高级设置中 IPv6 路由接管处于启用状态；最后检查节点配置，确认服务端支持 IPv6 出站。若节点只提供 IPv4 出口，客户端对 IPv6 目标的处理策略需要单独设定，否则会出现“接管了但发不出去”的静默失败。

```yaml
## 客户端全局配置要点（示意结构）
general:
  ipv6-support: true          # 启用 IPv6 解析与转发
  ipv6-in-tunnel: true        # IPv6 流量导入隧道
  dns-over-tunnel: true       # DNS 查询全部走隧道
  fake-ip:
    enabled: true
    ipv6-pool: "fd00:6968:656e::/64"   # Fake-IP 的 IPv6 映射池
```

Fake-IP 的 IPv6 映射池这一项容易被忽略。若只配置了 IPv4 映射池，AAAA 查询在 Fake-IP 模式下会返回空，应用回退 IPv4，虽然不泄漏但会丢失 IPv6 直连的收益；若映射池配置了 IPv6 段，返回的映射地址会被路由导入隧道，行为一致。

### 路径二：用规则强制 IPv6 走代理

路由接管之外，规则层是第二道闸。规则按顺序匹配，IPv6 目标若没有命中任何规则，会落到 FINAL 策略。把 FINAL 设为代理，或显式写一条 IPv6 兜底规则，可以堵住规则集的漏洞。

```ini
## 规则片段，注意顺序
[Rule]
## 国内 IPv6 段直连（按需精简）
IP-CIDR6,2400:3200::/32,DIRECT,no-resolve
IP-CIDR6,240e::/20,DIRECT,no-resolve
## 其余 IPv6 一律走代理
IP-CIDR6,::/0,PROXY,no-resolve
## 域名规则在后
DOMAIN-SUFFIX,example.com,PROXY
FINAL,PROXY,dns-failed
```

几个细节决定这条规则是否真的生效。`no-resolve` 表示匹配时不触发 DNS 解析，对纯 IP 规则必须加，否则会引入额外解析延迟与泄漏面。`::/0` 这条兜底规则必须放在具体 IPv6 段之后，否则国内段也会被送进代理。FINAL 的 `dns-failed` 参数让解析失败的域名也走代理，避免回退直连。

若使用规则集订阅，需要确认订阅里包含 IPv6 段。大量公开规则集只维护 IPv4 CIDR，IPv6 部分长期缺失，这是“规则模式泄漏”的高发原因。检查方法是打开规则列表，搜索 `IP-CIDR6` 关键字，若一条都没有，规则集在 IPv6 上是裸奔状态。

### 路径三：在内核层关闭 IPv6 解析

最彻底的做法是让设备根本不使用 IPv6。iOS 没有桌面系统那样的 sysctl 开关，但可以通过配置描述文件（Configuration Profile）限制网络行为，或在 Wi-Fi 设置中关闭该网络的全部 IPv6 能力。蜂窝侧无法逐网络关闭，但可以通过描述文件统一约束。

对普通用户更现实的做法是在客户端内关闭 IPv6 解析，让所有域名只返回 A 记录。这样应用层不会发起 IPv6 连接，网络层也就没有 IPv6 流量可泄漏。代价是纯 IPv6 站点不可达，国内主流站点均有 IPv4 入口，实际影响很小。

```yaml
## 关闭 IPv6 解析的配置取向
general:
  ipv6-support: false
  dns:
    strategy: ipv4-only
    query-types: ["A"]
```

这里有一个执行顺序的坑。关闭 IPv6 解析后，若系统缓存里还残留 AAAA 记录，应用可能仍尝试 IPv6 连接。切换配置后需要清空 DNS 缓存并重启客户端，iOS 上可通过飞行模式开关一次触发网络栈重建。

## 参数对比与选型

三条路径的适用场景不同，混用时的优先级也需要明确。

| 维度 | 开启 IPv6 转发 | 规则强制代理 | 关闭 IPv6 解析 |
| --- | --- | --- | --- |
| 接管层级 | 路由表 + 隧道 | 规则匹配 | 应用层解析 |
| 对纯 IPv6 站点 | 可访问（节点支持时） | 可访问 | 不可访问 |
| 泄漏堵截完整度 | 高（需节点支持） | 中（依赖规则集质量） | 高 |
| 对节点要求 | 需 IPv6 出站 | 无 | 无 |
| 延迟影响 | 双栈并发，通常更低 | 规则匹配开销可忽略 | 无 IPv6 路径 |
| 维护成本 | 中 | 高（规则需更新） | 低 |
| 适用场景 | 节点质量好、追求体验 | 精细化分流 | 稳定性优先 |

从工程实践看，推荐组合是“开启 IPv6 转发 + 规则兜底 + FINAL 走代理”。关闭解析作为兜底手段，在节点不支持 IPv6 出站时启用。单用规则强制代理而不开转发，会在 Fake-IP 的 IPv6 映射上出现不一致，表现为部分应用连接超时。

## 完整配置模板

以下模板覆盖 TUN、DNS、规则三段，可直接对照修改。

```yaml
## Shadowrocket 配置模板（结构示意）
tunnel:
  ipv4:
    included-routes: ["0.0.0.0/0"]
  ipv6:
    included-routes: ["::/0"]
    excluded-routes:
      - "fe80::/10"        # 链路本地不接管
      - "fc00::/7"         # 唯一本地地址不接管
  mtu: 1400                # 双栈下适当降低，规避分片
dns:
  servers:
    - "https://1.1.1.1/dns-query"
    - "tls://8.8.8.8:853"
  ipv6-servers:
    - "https://[2606:4700:4700::1111]/dns-query"
  fake-ip:
    enabled: true
    ipv4-pool: "198.18.0.0/16"
    ipv6-pool: "fd00:6968:656e::/64"
  fallback:
    - "223.5.5.5"
    - "119.29.29.29"
rules:
  - "IP-CIDR6,2400:3200::/32,DIRECT,no-resolve"
  - "IP-CIDR6,240e::/20,DIRECT,no-resolve"
  - "IP-CIDR,10.0.0.0/8,DIRECT,no-resolve"
  - "IP-CIDR6,::/0,PROXY,no-resolve"
  - "FINAL,PROXY,dns-failed"
```

MTU 这一项在双栈下值得单独说明。IPv6 头部比 IPv4 多 20 字节，隧道封装再叠加一层，若 MTU 仍按 1500 配置，大包会触发分片或 PMTUD 黑洞，表现为部分 HTTPS 站点加载卡死。1400 是一个保守且通用的取值，蜂窝网络下可进一步降到 1380。

DNS 的 fallback 列表用于国内域名解析，与远端解析策略配合。若使用 Fake-IP，fallback 只在映射未命中时触发，泄漏风险低；若使用远端解析，fallback 的查询会从本地发出，需要确认这些上游不返回带地区属性的 AAAA 记录。

## 排查流程

按顺序执行，每步都有明确的判定标准。

```bash
## 步骤 1：确认当前网络是否分配了 IPv6
## iOS 上可通过快捷指令或同网段电脑执行
ifconfig | grep "inet6" | grep -v "fe80"

## 步骤 2：确认 IPv6 默认路由指向
netstat -rn -f inet6 | grep default

## 步骤 3：确认隧道接口是否接管 ::/0
## 若 default 指向 utun，接管成功；指向 en0/pdp_ip0，接管失败

## 步骤 4：双栈出口比对
curl -4 -s https://ipinfo.io/ip
curl -6 -s https://ipinfo.io/ip

## 步骤 5：DNS 出口比对
dig +short AAAA example.com @1.1.1.1
dig +short AAAA example.com
```

判定标准逐条对应。步骤 1 若无 IPv6 地址，泄漏面为零，无需修复。步骤 2 与 3 的默认路由指向决定接管是否成立，这是根因所在。步骤 4 两个地址的 ASN 一致才算通过。步骤 5 两条查询返回的 AAAA 记录若不同，说明解析链路分裂，需要检查 DNS 接管。

### 常见失败模式与对应处置

第一种，开关已开但路由未接管。原因是客户端版本或配置未下发 `::/0`，处置是重建配置或升级客户端。

第二种，路由已接管但连接超时。原因是节点不支持 IPv6 出站，处置是关闭 IPv6 解析或更换支持双栈的节点。

第三种，规则集缺 IPv6 段导致部分泄漏。处置是补 `IP-CIDR6` 兜底规则，并定期检查订阅更新。

第四种，DNS 泄漏伴随 IPv6 泄漏。处置是启用 DNS over tunnel，并把 IPv6 DNS 服务器一并纳入隧道。

第五种，WebRTC 候选泄漏。处置是确认路由接管完整，iOS 上可额外通过内容拦截规则限制 WebRTC，但根治仍在网络层。

## 修复后的验证清单

修复完成不等于验证通过，逐项核对。

| 检查项 | 方法 | 通过标准 |
| --- | --- | --- |
| IPv4 出口 | curl -4 或面板 | 属于节点 ASN |
| IPv6 出口 | curl -6 或面板 | 属于节点 ASN，或不可达 |
| DNS 出口 | 面板 DNS 区块 | 不出现本地运营商地址 |
| WebRTC 候选 | 面板 WebRTC 区块 | 无本地 IPv6 段 |
| 路由接管 | netstat -rn -f inet6 | default 指向 utun |
| 规则覆盖 | 规则列表搜索 IP-CIDR6 | 存在 ::/0 兜底 |
| 应用可用性 | 访问国内主流站点 | 正常加载，无超时 |
| 纯 IPv6 站点 | 访问 ipv6.google.com | 按配置预期，可达或明确不可达 |

清单里“纯 IPv6 站点”这一项容易被跳过。它的价值在于区分“接管成功但节点无 IPv6 出站”与“接管失败”。若该站点不可达但 IPv6 出口探测显示节点地址，说明接管正常、出站受限；若探测显示本地地址，接管失败。

## 关于节点侧的一个补充

本地修好之后，出口质量仍取决于节点。IPv6 出站的可用性、ASN 归属、以及是否做了地址族一致性处理，都会影响探测面板的最终呈现。部分服务商在双栈节点上只广播 IPv4 的 anycast，IPv6 走的是另一条路径，导致两个地址族的地理位置不一致，面板会判定为异常。

选择节点时可以关注几个技术指标：是否提供原生双栈、IPv6 前缀的注册地与实际机房是否一致、DNS 解析是否在节点侧完成。光速云这类服务商在双栈支持上提供了较完整的出站配置，适合作为修复后的对照基准。具体选型仍以自身网络环境与探测结果为准，本地接管完整是前提，节点质量是加成。

## 收尾时值得记住的几点

IPv6 泄漏的本质是路由接管范围与应用解析行为之间的错位，修复的核心动作是让 `::/0` 真正进入隧道，或者让应用层不产生 IPv6 流量。探测面板是证据，命令行是交叉验证，两者结合才能定位断点。规则集的 IPv6 段缺失是最常见的隐性原因，定期检查 `IP-CIDR6` 的存在性比事后排查省事得多。MTU 与 DNS 这两个看似边缘的参数，在双栈环境下会直接影响可用性，配置时一并纳入考量。修复完成后按清单逐项核对，尤其是纯 IPv6 站点那一项，它能区分“接管成功”与“出站受限”两种截然不同的状态。
