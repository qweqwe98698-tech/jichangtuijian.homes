代理连上了，别的网站都正常，偏偏 ChatGPT 打不开——这说明你遇到的不是连通性问题，而是**解锁与身份判定**问题。这两类故障的排查方法完全不同，用错方法会白白折腾很久。

## 症状分诊：四种「打不开」不是同一件事

先确认你属于哪一种，后面的顺序会因此改变：

- **完全打不开**：页面转圈、白屏、连接被重置。
- **地区提示**：页面能加载，但提示当前地区不可用。
- **验证循环**：每次访问、甚至每次刷新都要过一遍人机验证。
- **中途断流**：能正常提问，长回答写到一半停住或报错。

## 排查次序一览表

| 症状       | 先查             | 再查             | 最后查             |
| ---------- | ---------------- | ---------------- | ------------------ |
| 完全打不开 | 分流规则是否漏放 | 节点本身是否可用 | 客户端与 DNS       |
| 地区提示   | 出口 IP 所属地区 | 浏览器身份残留   | 账号注册地区       |
| 验证循环   | 出口 IP 共享程度 | 浏览器指纹与插件 | 频繁切换节点的行为 |
| 中途断流   | 链路稳定性       | 客户端超时设置   | 使用中切换了节点   |

## 检查点 A：出口 IP 是否被判定为不可用地区

这是命中率最高的一条。**判断依据**：在代理状态下打开任意一个显示当前 IP 与归属地的页面，看两件事——归属地是不是你以为的那个地区，以及它是不是被标注为数据中心 IP。

- 归属地不对 → 换到明确支持该场景的节点分组。多数机场会把这类节点单独分组或加标记。
- 归属地正确但仍被拒 → 说明这个 IP 段本身被判定过，同一分组里换几个不同出口再试。

一个常见误解是「延迟低的节点解锁能力就强」。两者没有关系：解锁看的是出口 IP 的属性，延迟看的是链路质量。挑节点的思路见 [AI 场景选型](/best/ai/)与 [ChatGPT 机场专题](/chatgpt-airport/)。

## 检查点 B：浏览器里的身份残留

节点换对了还是看到地区提示，问题多半在浏览器：上一次访问留下的 Cookie、本地存储和会话，仍然在告诉对方你在别处。

按这个顺序试，成本从低到高：

1. **开无痕窗口**重新访问一次——最快的验证方式，成功即锁定原因。
2. 清除该站点的 Cookie 与本地存储，重新登录。
3. 关闭可能改写请求的浏览器插件（广告拦截、隐私保护、翻译类都可能干扰）。
4. 换一个浏览器交叉验证。

**注意时序**：一定要先连好节点再打开页面，而不是页面开着再去切节点。

## 检查点 C：分流规则漏掉了相关域名

如果你用的是规则分流模式，只要相关域名没被规则覆盖，这部分请求就会以直连方式发出，表现为「网页能开但功能不可用」「网页版正常但 App 不行」。

**判断依据**：临时切换到全局代理模式访问一次。全局下正常 → 就是规则漏放，回去把该服务涉及的域名归入代理策略即可；全局下依然不行 → 排除规则问题，回到检查点 A。规则编辑位置见 [Clash 教程](/apps/clash-guide/)。

## 检查点 D：验证循环与长任务断流

**验证循环**通常指向出口 IP 上的用户密度：同一个 IP 后面挂着大量用户时，被要求反复验证是很自然的结果。换用共享程度更低的节点是唯一有效的方向；不要去找绕过验证的办法。

**长任务断流**要查的是链路的持续稳定性，而不是解锁能力：

- 生成过程中**不要切换节点**，那会直接掐断这条连接。
- 检查客户端是否设置了较短的空闲超时。
- 如果断流集中出现在晚间，那是拥塞而不是解锁问题，见[晚高峰慢的排查](/fix/peak-hour-slow/)。
- 对长连接敏感的场景，专线类线路的表现通常更平稳，差别见 [IPLC 与 IEPL 的区别](/learn/iplc-vs-iepl/)。

## 换机场之前先确认的事

在把原因归给机场之前，先完成一次交叉验证：**同一台设备、同一个浏览器、换另一个订阅**再试一次。另一个订阅正常，说明当前机场在这个场景上的出口不合适；两个都不正常，问题在你的浏览器或账号侧。

预防上有三个习惯值得养成：固定使用一到两个验证过可用的节点，不要频繁换；把这类服务的域名一次性配好分流规则，避免每次手动切全局；不要把「能打开」当成长期承诺——出口 IP 的判定会变化，选机场时看它是否持续维护这类线路，而不是看某一天的截图。

如果连节点本身都连不上，那属于另一条排查路径，见[节点全部超时怎么办](/fix/nodes-all-timeout/)。
